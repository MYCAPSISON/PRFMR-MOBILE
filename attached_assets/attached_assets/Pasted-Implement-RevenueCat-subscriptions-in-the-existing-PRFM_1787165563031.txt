Implement RevenueCat subscriptions in the existing PRFMR Expo/React Native mobile app.

Before making changes, audit the current authentication, database, navigation, subscription/paywall, environment-variable, and app-startup architecture. Reuse the existing architecture wherever possible and avoid unrelated refactors.

==================================================

RevenueCat entitlement identifier:
PRFMR Pro

RevenueCat default Offering identifier:
default

Current valid iOS products:

Monthly:
prfmr_pro_monthly

Annual:
prfmr_pro_annual

App Store subscription group:
PRFMR Pro

IMPORTANT:
Do NOT use these obsolete iOS product identifiers:

prfmr_monthly

==================================================
1. REVENUECAT SDK
==================================================

Install/configure:

react-native-purchases
react-native-purchases-ui

Use versions compatible with the current Expo/React Native version.

Configure RevenueCat exactly once during native app initialization.

Use platform-specific PUBLIC RevenueCat SDK keys:

EXPO_PUBLIC_REVENUECAT_IOS_API_KEY
EXPO_PUBLIC_REVENUECAT_ANDROID_API_KEY

The Android key may be absent temporarily while Google Play subscription configuration is incomplete.

Never expose any RevenueCat secret key, Apple private key, App Store Connect API private key, or Google service-account credentials in the mobile app.

Enable RevenueCat DEBUG logging only in development/test builds.

==================================================
2. REVENUECAT CUSTOMER IDENTITY
==================================================

PRFMR already has authenticated users.

After authentication, call RevenueCat using the existing stable internal PRFMR user/database ID:

Purchases.logIn(<stable PRFMR user ID>)

Do not use:
- email
- display name
- Apple relay email
- Google email

as the RevenueCat App User ID.

Handle correctly:
- first login
- persisted session
- app restart
- logout
- switching accounts

On logout, use RevenueCat's supported logout/reset flow and clear account-specific subscription state before identifying the next user.

==================================================
3. ENTITLEMENT
==================================================

Use this exact RevenueCat entitlement identifier:

PRFMR Pro

Premium access must depend only on whether this entitlement is active.

Conceptually:

const customerInfo = await Purchases.getCustomerInfo();

const isPro =
  customerInfo.entitlements.active['PRFMR Pro'] !== undefined;

Do not determine premium access based on:
- product ID
- monthly vs annual
- trial state
- founding state
- locally stored booleans

RevenueCat entitlement state is the premium-access source of truth.

default

==================================================
6. FOUNDING USERS
==================================================

PRFMR has existing founding users.

The authoritative source is:

users_auth.is_founding

If:

users_auth.is_founding === true

the user is a founding user.

Do not infer founding status from:
- signup date
- email
- local storage
- install date
- RevenueCat anonymous ID
- client-provided values

Do not permit client code to write or modify is_founding.

==================================================
7. FOUNDING CUSTOMER ATTRIBUTE
==================================================

After RevenueCat has been identified with the authenticated PRFMR user ID, synchronize founding eligibility to RevenueCat.

For founding users:

founding_user = "true"

For non-founding users, ensure stale founding state does not persist incorrectly.

The database remains authoritative.

The RevenueCat attribute is for targeting/presentation only.

Do not use a client-controlled attribute as the sole security mechanism.

==================================================
8. FOUNDING OFFERING
==================================================

Support a separate RevenueCat Offering for founding users.

Conceptually:

default
founding

If a founding Offering does not already exist, do not invent store products or discounted prices in code.

Instead, structure the app so that the founding Offering can be configured remotely in RevenueCat after the corresponding Apple/Google store offers are created.

Founding commercial terms:

YEARLY:
30% off for the first year

MONTHLY:
25% off for the first year

After the promotional period, the subscription renews at the standard applicable subscription price.

Do not calculate discounted prices in JavaScript.

Do not hard-code GBP/USD amounts.

Do not process subscription payments through the backend.

Apple App Store / Google Play must define the actual promotional billing terms.

RevenueCat should present the appropriate store-defined offer.

==================================================
9. OFFERING SELECTION
==================================================

Prefer RevenueCat Targeting.

Desired logic:

founding_user == "true"
    -> founding Offering

otherwise
    -> default Offering

If RevenueCat Targeting is not yet configured or unavailable in the current setup, implement one centralized offering-selection layer rather than duplicating checks throughout screens.

Do not scatter:

if (is_founding)

logic throughout the UI.

==================================================
10. FOUNDING PAYWALL UX
==================================================

The founding paywall should clearly communicate:

FOUNDING MEMBER OFFER

Thanks for helping build PRFMR.

YEARLY

MONTHLY
25% off for your first year

The actual localized store prices must come from RevenueCat / StoreKit / Google Play.

The paywall must accurately disclose what happens after the promotional period.

Do not state:

- 25% off forever
- lifetime founding price

unless the underlying store configuration actually provides that.

==================================================
11. STANDARD 7-DAY INTRODUCTORY TRIAL
==================================================

Normal subscriptions may use store-configured 7-day introductory free trials.

Do not implement trial timing manually.

Do not create a local 7-day entitlement timer.

Do not assume founding promotional offers stack with introductory trials.

Display only the trial/offer for which the store reports the user is eligible.

==================================================
12. PAYWALL PRESENTATION
==================================================

Use:

react-native-purchases-ui

Use the RevenueCat Paywall Builder paywall.

For normal users, use the default Offering.

For founding users, use the founding Offering once it exists/configures successfully.

Do not present a paywall if the `PRFMR Pro` entitlement is active.

Wait until:
- authentication is resolved
- RevenueCat is initialized
- the RevenueCat customer has been identified
- CustomerInfo has been fetched

before deciding whether to show the paywall.

Avoid startup paywall loops.

==================================================
13. PURCHASE COMPLETION
==================================================

After successful purchase:

1. Refresh CustomerInfo.
2. Confirm `PRFMR Pro` is active.
3. Update application subscription state.
4. Dismiss/leave the paywall.
5. Unlock premium functionality.

Do not rely solely on a purchase-success callback boolean.

Entitlement state is authoritative.

==================================================
14. RESTORE PURCHASES
==================================================

Provide an accessible Restore Purchases action.

After restore:

- refresh CustomerInfo
- update premium state
- dismiss paywall if entitlement is active
- handle no-purchase/error states gracefully

15. CENTRALIZED SUBSCRIPTION STATE

Create one centralized subscription service/provider/hook.

- isPro

==================================================
16. CUSTOMERINFO UPDATES
==================================================

Register RevenueCat CustomerInfo update listeners.

Clean them up correctly.

Refresh at sensible lifecycle points:

- authentication success
- restored persisted session
- app startup
- purchase completion
- restore completion
- app foreground where appropriate

Do not create excessive requests.

==================================================
17. ACCOUNT SWITCHING SECURITY
==================================================

When User A logs out and User B logs in:

User B must never temporarily inherit:

- User A's Pro status
- User A's founding status
- User A's Offering
- User A's CustomerInfo

Clear account-specific local subscription state during the transition.

Identify the new RevenueCat user and fetch fresh CustomerInfo before unlocking premium features or presenting an account-specific paywall.

==================================================
18. ERROR HANDLING
==================================================

Handle gracefully:

- RevenueCat initialization failure
- offering unavailable
- products unavailable
- store unavailable
- network unavailable
- purchase cancelled
- purchase pending
- purchase failed
- restore failed
- CustomerInfo fetch failed

Purchase cancellation is not an application error.

Do not unlock Pro when subscription status is unknown.
